# 一括生成のCSSメモリ診断

基点cf410104。以前のX3ログdevice-monitor-260926-235308.logではCSS開始前の空きが約62.7〜63.1KBで、Epub::parseCssFilesの64KiB条件を下回った。これは最大連続領域の不足を直接示すログではなく、総空きheapによる開始拒否。修正済みのparser cleanup assertとは別件。

一括生成はfindEpubFilesで全EPUBパスをvector<string>に保持し、全処理と最後の状態集計が終わるまで解放しない。日本語パスはUTF-8バイト数で保持されるため、冊数・長い書名によるメモリ増加が候補。ただし以前のログに冊数・保持量がないため原因未確定。load前にはfont cache、kern/ligature、resident SD font cachesを既に解放している。垂直字形や活動スタックの残存量も実測次第。

診断専用env:batch_css_memoryではBCMEMをINFO出力する。走査前後、一覧の容量、各書籍開始・font解放前後・load前後・書籍ローカル破棄後、各CSS開始判定を記録。一覧容量はstd::string SSOとallocator overheadを含む正確なheap使用量ではないため、実heapの前後差と併読する。book-releasedの計測用RAIIはepubより先に宣言し、continue/break時も破棄後を観測する。

診断は計測だけであり、閾値・解放方針・キャッシュ形式・生成順序を変えない。通常ビルドでは追加ログを無効化。ログ出力自体の時間影響はある。

## 実機手順

X3のみ先行。以前エラーが出た、多数の書籍を入れたSDカードを使用。全消去は不要。CSSキャッシュ生成も測るには確認用の1冊だけキャッシュを削除する。他の書籍やフォントはそのまま。再起動し、ログ記録開始後、一括生成を開始。全体が長い場合は最初の数冊が進んだところで中断してよい。ログを保存して解析する。診断を終えるまで原因確定・修正完了とは扱わない。

## 実測とSD一覧への変更

X3 device-monitor-260927-104529.log: 498冊。走査前free=133476、走査後70648（62828bytes減少）。vector容量12288bytes、パス文字列容量40579bytes。63冊目まで書籍破棄後はおおむね70288bytesに戻る。継続的なリークより、全件一覧の常駐が支配的な要因と判断した。今回CSS開始拒否は0件だが、ZIP inflate初期化失敗54件、CSS unavailableによる章未完了56件。これら全ての原因・解決は修正版の実機比較待ち。

BatchEpubPathsは/.crosspoint/.batch-epub-paths.tmpに2byte長＋UTF-8パスを保存する。毎回truncateして新規作成し、完了・中断・異常終了の通常アンワインド時に削除。電源断で残っても次回は再利用せず上書きする。永続キャッシュ形式には影響しない。走査順は従来通り。件数はRAMの整数だけで保持し、生成と集計時に1件ずつ読み出す。途中走査中断なら、確実に書けた分の状態だけを集計する。

作成・書き込み・close/sync・再open・seek・レコード読み込み・ファイル長確認が失敗した場合はSDエラーとして止める。2byteの長さのため単一パスは65535byteまでで、超過は失敗として扱い切り詰めない。既存HALのディレクトリ列挙APIは終端とI/O失敗を区別する詳細結果を公開していないため、ディレクトリ列挙中の全I/O異常を検知できるとまでは主張しない。

ホストテストは本物のBatchEpubPathsをSD代替実装で実行し、日本語・記号・改行、複数回の読み返し、空一覧、走査中断相当の部分一覧、500冊、create/write/close/reopen/size/seek/read失敗、不正レコード長、一時一覧の後始末を確認。実SDでの同期書き込み時間、メモリ改善量、生成結果はX3/X4実測待ち。

修正版のX3テストでは同じ498冊のSDカードを使い、他の本を削除・移動しない。キャッシュ全消去は不要。未完了本はそのまま再開可能。前回のように一括生成し、最初の数冊が進んだところまででもログを取得する。BCMEMの走査前後とZIP/CSS失敗件数を比較してから完走・中断再開・再実行・X4へ進む。
