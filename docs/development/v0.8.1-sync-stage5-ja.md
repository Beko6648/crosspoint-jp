# v0.8.1 Stage 5: WebUIで共有JSONを受け渡す

2026-10-01。基準コミット7bcbd933。開発版の版表示はv0.8.0のまま。

## 操作

1. 端末で対象のEPUBを一度開いてから閉じる。読書位置・設定などを通常どおり保存する。
2. Wi-FiのWebサーバーを開始し、PC/スマートフォンのブラウザで端末のWebUIを開く。
3. ファイル管理の対象EPUBの「共有」を選ぶ。本のタイトルを確認する。
4. 読書位置・しおり・本の設定・本別履歴を選び、「選んだデータを書き出す」。BookId.jsonをPC等へ保存する。EPUB本体は含まない。
5. 受信端末にも同じEPUBを置いて一度開き、同様にWebUIでその本の「共有」を開く。
6. JSONを選び「共有ファイルを端末へ送る」。同じ本の受信済み共有JSONを置き換える確認が出る。
7. 受信成功後、Wi-Fiを終了して同じ本を開き、読書メニュー→ツール→「SDで読書データを共有」→取り込みで比較・種類選択して適用する。

Web受信は/YomukaSync/<BookId>.jsonを保存する段階。読書データへ適用する操作は端末の既存確認画面を使う。設定を含む取り込みは完了画面の決定でHomeへ、その他のみは本を開き直す。
EPUBの移動などで現在のパスのメタデータがなければ「この本を端末で一度開いてから再試行」と案内する。
読書位置が保存されていない場合は読書位置の選択を外して書き出す。

## 実装

- /sync: Web共有画面。ファイル管理からbookクエリーでEPUBを選ぶ。
- GET /api/sync/book: EPUBのBookId、章数、タイトルを確認。既存メタデータを読み、CSS/フォントや組版を読み込まない。
- GET /api/sync/export: SD版と同じexportSnapshotと更新日時ポリシーで、選択した1〜15の種類マスクを出力。Cache-Control: no-store。書き出しはダウンロードで、共有ファイルの上書きはしない。
- POST /api/sync/upload: 1リクエスト1ファイルのmultipart。64KiB以下のデータをサイズと空きメモリを確認しながらRAMに蓄積。完了したPOST全体の厳密UTF-8/JSON/仕様検証後、同じEPUBか確認する。
- 保存はStorageIoの一時書込み・読戻し確認・旧ファイルへの復旧を使う。入力の任意パス/名前を保存先に使わず、検証済みBookIdで固定する。
- 中断、複数ファイル、空/過大/不正JSON、メモリ不足、異なるBookId/章範囲で保存を拒否。通信中は本の設定やprogress.binなどを変更しない。
- サーバー終了時は受信中のRAMを解放。中断後の新しいリクエストを受け付ける。
- ブラウザでは基本形式/サイズ/BookIdを先に確認し、通信と本文受信に30秒のタイムアウトを設定。送信中は多重操作を抑制する。厳密検証は端末側でも行う。

## 検証と限界

ホスト: 実際のアップロード状態と保存処理の156チェック（分割受信、完了前の拒否、中断と再試行、複数ファイル、過大、メモリ不足、不正JSON、別の本、共有ファイル保存失敗、読書保存データ不変）。Nodeで実際の画面JSの28チェック（種類選択、ダウンロード、確認キャンセル、別の本、サイズ、通信失敗、HTTPエラー、再操作）。ブラウザで実HTMLをローカル模擬APIに接続し、タイトル・日本語・初期状態の表示を確認。模擬APIは実機のWi-FiやHTTP処理の証明ではない。

通信がPOST完了前に中断すれば受信JSONを公開しない。完了後に応答だけ失われた場合は、受信結果が不明になる可能性がある。再接続して確認し、必要なら再送する。どちらでも読書データの適用には端末の確認が必要。
64KiB以内でも空きメモリにより拒否する。ブラウザだけで読書データの直接適用はしない。
初回Web接続フリーズとWi-Fi終了問題は今回原因修正したとはしていない。以下の実機試験で継続確認する。

## 実機確認（X3/X4）

1. Webサーバーの初回起動→ブラウザ表示→共有画面が開き、本のタイトルが一致する。
2. 4種類/1種類の書き出しが成功し、同じJSONをSD版と受け渡せる。
3. 相手端末のWebUIへ受信→Wi-Fi終了→同じ本の端末確認画面で適用できる。
4. 別の本、不正JSON、選択なし、取り消しで対象の保存データが変わらない。
5. 確認用ファイルで転送中断と再送を行い、読書データに変化がない。64KiB超のファイルが拒否される。
6. Web利用後にWi-Fiを終了し、本の表示・設定・しおり・履歴が正常に戻る。設定取り込み後のHome移動も確認する。

## 利用者による実機確認結果（2026-10-01）

X4はWeb共有の確認OKとの報告。X3は初回の受信で不正・過大・通信中断・メモリ不足の可能性を示すエラーが出たが、再起動後は受信に成功し、Wi-Fi終了後の端末取り込みと読書データ反映までOKとの報告。報告後のコード変更は行っていない。初回失敗の原因は未確定で、再発時に調査する。上記の異常系や全項目を個別に実機確認済みとはしていない。

## X3受信失敗の再現調査

利用者による同一JSONの比較で、再起動直後の受信は成功、読書後は失敗し、再起動なしの再送も失敗した。原因はまだ未確定。診断版は受信条件を緩めず、HTTPエラー本文にreason（memory / too-large / invalid-state / multiple-files / aborted / validation / incomplete-or-empty）、validation（SnapshotError値）、bytes、needed、free、largestを表示する。neededが非0のfree/ largestは最初の容量・メモリ判定拒否時点、その他は失敗応答生成時点の値。bytesは保持中バッファ長であり、失敗時解放後は0になり得る。JSON本文や本のパスは診断に含めない。X3でA/B比較を再実施し、失敗時の表示全文を記録して原因を絞る。

診断版の実機報告: 同一X3でPCへ書き出した753バイトJSONを送り戻すとmemory、free=32528、largest=19444。読書後はmemory、free=29088、largest=16372。判定の総空き要求は753*3+32768=35027、連続領域要求は753+4096=4849で、双方とも総空き条件で拒否された。根本的なメモリ保持元はまだ特定済みとはしていない。

次の試験版ではWeb活動開始時とサーバー生成直前に、通常キャッシュに加えて再構築可能なSDフォント縦書き字形を解放する。受信・書き出しの余裕判定を変更しない。縦書き字形は読書再開時に読み直す既存経路を使用。実機では再起動直後、読書後、書き出し後の受信と、Wi-Fi終了後の縦書き句読点・括弧・ページ送りを確認する。SDフォント非使用時やHTTP接続中に保持される領域への効果は未確認。改善しなければ診断表示を使って継続調査する。

縦書き字形解放試験版でもPC書き出し後の受信はfree=32916/ largest=19444、読書後はfree=29556/ largest=26612で失敗。総空きの旧判定には届かなかった。

次の修正版では受信メモリの許可見積もりをmin(16*受信サイズ+8192, 3*受信サイズ+32768)に変更する。小さなJSONにも読書用32KiB領域を一律要求していた旧条件を外し、JSONスロット・復号キー・厳密スキャナーの一時領域を想定したサイズ依存の余裕を設ける。大きい入力は旧判定を維持。連続領域は受信サイズ+4096、最大65536バイト制限を維持。753バイトの総空き要求は35027→20240バイト。これは許可見積もりであり、すべての入力や実機での確保成功を保証する数学的な上限ではない。

受信バッファは長さを明示したnothrow配列で確保し、確保失敗時はallocationとして拒否・解放する。検証直前にもメモリ条件を再確認する。受信バッファは検証成功後、EPUB情報の読込み・共有JSONの保存より前に解放。厳密JSON検証、BookId一致、読戻し確認・バックアップ付き保存、端末上の適用確認は維持。修正版の実機効果は下記の利用者確認結果を参照。
