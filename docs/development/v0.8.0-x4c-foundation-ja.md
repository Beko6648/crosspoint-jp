# v0.8.0 X4C/X4V2基盤整理（Stage 2）

Stage 1の `373d1817` から `feat/v0.8.0-x4c-foundation` を作成。
同じworktreeを再利用し、SDKは `18e73e16a1965fb19c62fa3a717cbc3a5b43add3` に固定。
X4 Classic/X4 V2は引き続きExperimental。実機なしのため正式対応・消費電力改善は宣言しない。

## 今回の修正

デバッグ表示有効時の電源ログは、従来「X3以外」を通常X4として処理していた。
X4Cではその結果GPIO0をADCとして読み、機種名をX4、USB状態を未接続と記録していた。
SDK profileのGPIO0はナビゲーションボタン、電池はCW2017、USB検出ピンは未定義であり、この診断は不適切だった。

- X4C専用のコンパイル分岐でSDK `BatteryMonitor::readStatus()` を利用する。
- 電圧の取得失敗は `-1` にし、ADC・電流・USBの未対応値を正常な測定値と区別する。
- 通常X3/X4の既存ADC/BQ27220処理と電源制御は維持する。
- 手動診断レポートにSDK/build ID、controller選択根拠、VER認識・timeout、profileのI2C/SDMMC構成を残す。
- snapshotを参照するだけで、レポート保存中の再probe・NVS書き込みは行わない。

## 経路点検

| 項目 | コード上の確認 | 実機で残る確認 |
|---|---|---|
| 機種選択 | S3固定X4Classic profile。C3のI2C fingerprintを実行しない | 基板variantとの一致 |
| controller | InputManager/SPI初期化前にNVS優先/VER fallback。Stage 1 hostテスト通過 | NVSあり/なし個体の表示、未知VER |
| RTC | SDK Pcf8563経路（BM8563互換）、0x51、SDA39/SCL38。VLフラグ時は時刻読取失敗 | 有効/無効sleep、時刻保持 |
| 電池 | CW2017、0x63、同じI2Cバス。X4CのADC診断を除去 | 実電圧、読み取り失敗からの復帰 |
| SDMMC | 1-bit CLK41/CMD42/D0=40。通常sleep前にStorage.shutdown→SDK host停止/信号ピン解放 | 書き込み後の停止、wake再マウント、消費電力 |
| 電源 | C3 X4のGPIO13 latch処理はC3限定。X4CのGPIO13はdisplay CS | レール停止とRTC保持の両立 |
| USB | 確認済み検出ピンなし。今回は診断値をunknownに修正 | ケーブル検出手段・充電STAT極性 |
| IMU | profileにはQMI8658があるがYomukaはX3のみ有効 | X4Cの実装向き、感度、操作設計 |
| wake理由 | 現HALはC3寄りの分類。S3のEXT1 wakeはOther扱いになり得る | ボタン保持判定・起動理由の整合。分類変更は今回は行わない |
| Recovery | Yomuka独自SD更新/recoveryを維持 | X4Cの物理キー、適合bin検査、実書き込み |

RTC、SDMMC、電源、Recoveryの実装自体は今回変更しない。
全体のDeviceCapabilities化、#3652、USB MSC、BLE、追加機種への対応拡大は対象外。

## host検証

`python3 test/run_x4c_foundation_test.py`:

- 実際の `appendPowerLog()` をhost用に取り出してcompile/run。
- X4CではADC・C3 I2C APIをstubにも用意せず、その経路が混入するとcompileを失敗させる。
- CW2017電圧成功/失敗、機種名、USB不明、debug OFF無出力を確認。
- X3/X4では従来のログ値・ADC/BQ経路を確認。
- 実SDKのX4C profileを使い、診断レポートのNVS/VER/未知ID/timeout・I2C/SDMMC設定を確認。

加えて `python3 test/run_freeink_stage1_test.py` で検出protocolとX3のIMU補正OFFを確認。
これらはhostでのコード検証であり、実際のCW2017通信・電気特性・画面表示を証明しない。
