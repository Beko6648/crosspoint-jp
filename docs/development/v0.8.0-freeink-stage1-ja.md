## Deep-sleep abort診断

`setup()` のSerial初期化後、既存recovery判定より前に
`powerManager.captureBootDiagnostics()` を呼ぶ。SIMULATORでは呼ばない。
`HalPowerManager::captureBootDiagnostics()` がSDKの `takeAbortedSleepInfo()` を一度だけ消費し、
独自HALの小さな構造体に保持する。重複呼び出しでも再取得・再ログしない。

異常記録がある場合だけ、INFOレベルで次を出す。

```text
[PWR] Previous deep-sleep entry aborted cause=<数値> wake_pin=<数値>
```

既存の手動診断レポート `/.crosspoint/diagnostics/report_*.txt` に追加する項目:

```text
previous_deep_sleep_aborted=false または true
previous_deep_sleep_abort_cause=<数値>       # trueの場合のみ
previous_deep_sleep_abort_wake_pin=<数値>    # trueの場合のみ
```

通常bootではabortログを出さない。情報はそのboot中にRAMで保持し、何度レポート保存しても参照できる。
追加NVS書き込み・自動SD保存・Yomuka側の追加RTC永続化はない。
SDKが持つRTC記録以外には、既存ログリングの仕組みだけを使う。

### SDK #104の復旧コードが除去される件（追加調査により判断更新）

今回使ったframeworkの `esp_sleep.h:622` は次の宣言を持つ。

```cpp
void esp_deep_sleep_start(void) __attribute__((__noreturn__));
```

候補SDKの `PowerManager::deepSleep()` はこの関数呼び出しの後にRTC記録と `esp_restart()` を置く。
しかし実ビルドの逆アセンブルでは、C3もS3もこの後続処理が存在しない。

- C3: `esp_deep_sleep_start` 呼び出しで関数が終わり、直後は次の関数。
- S3: 同呼び出しの次は `ill`。RTC書き込みと `esp_restart` はない。
- `takeAbortedSleepInfo()` 自体はリンクされ、診断取得コードは存在する。

従って、今回のhost診断テストで証明したのは**既にabort記録が存在する場合のYomuka側の扱い**。
実機上の異常復旧・RTC記録の生成が有効になったことは証明できず、現toolchainでは期待のコードが消えている。
これは新しい通常sleep回帰を実測したという意味ではなく、候補SDKの追加機能が成立していないという問題。
Issue #40の原因確定・解決とも無関係。

指定revisionの評価を保つためSDKへ独自パッチは加えていない。
追加調査では、実際にリンクされたIDF関数内部にC3/S3とも `abort()` があることを確認した。
SDK呼び出し元へ戻る契約ではなく、従来のSDK busy loopもこのAPIでは到達しない。
従って新たなsleep回帰や復旧手段の欠落を示す証拠ではない。以前の「修正まで実機確認を止める」という判断を訂正する。
戻り値を扱う `esp_deep_sleep_try_to_start()` はsleep rejectionを許可する別のAPIであり、今回は置換しない。
#104を有効な機能として採用する場合は、別途API方針と異常注入検証が必要。

## 機種別の影響

### X3

- `XTEINK_X3` / `XTEINK_X3_UC8279` とも `imuSwapXY`, `imuFlipX`, `imuFlipY` はfalse。実profileをstatic_assertで確認。
- SDKの `Imu::read()` はswap→flipの順で補正するが、X3では通らない。
- `HalTiltSensor.cpp` は変更なし。通常mappingは縦 `gx`、逆縦 `-gx`、横CW `-gy`、横CCW `gy`。
  傾き反転設定では各符号が反転する。診断画面の左右表示の既存符号も維持。
- QMI8658の初期化・感度・閾値・poll・sleep/wake設定の変更なし。
- UC8253 / X3用UC8279 driverは今回の差分対象外。X3のVERプロトコル回帰も通過。

### 通常X4（ESP32-C3）

- Yomukaは従来通りSSD1677 profile。X4の `HalGPIO::begin()` では追加VER probeを行わない。
- SDKのSSD1677 driver変更なし。X4系UC8179/UC8279 driverは共通binaryに含まれ得るが、通常X4の選択は変わらない。
- `HalPowerManager::startDeepSleep()` のX4専用GPIO13 latch解放は変更なし。通常X4は外部RTCなしのためfull power-off経路を使う。RTC設定の切り替え・時刻保持はX4の確認対象外。
- abort復旧の制限は上記の通り。正常sleep/full power-offは実機未確認。

### X4 Classic / X4V2（ESP32-S3、Experimental）

- `HalGPIO::begin()` は固定X4C profileのまま `applyXteinkDisplayController()` を呼ぶ。
  InputManager / SPI初期化より先なので、SDKのbit-bang VER probeと整合する。
- NVS `hw_calib/screenType` が存在すれば最優先。`1/0x0B → UC8179`, `2/0x0C → UC8279`, その他 → SSD1677。
  この場合VER probeをしない。
- NVSがなければVERを読む。`0x01 → UC8179`, `0x02/0x68/0x69 → UC8279`。
- **未知VER（0x00/0xFF/0x03/0x67など）のfallbackは、このcommitではUC8279**。
  事前会話のSSD1677 fallbackとは異なる。0x03/0x67を正式認識するrevisionではない。
- 初期probe時のSDK直接Serial出力は開始タイミングにより失われるため、
  起動後にSDK診断snapshotと実選択controllerから `source=NVS` または `source=VER` をINFOログへ再記録する。
  VERの場合はid、recognized、busy_timeoutも残す。二度目のprobeやNVS変更は行わない。
- このsource判定は、現commitで `diag.valid` が「NVSなしでprobe実施」を意味し、
  Yomukaが起動中に一度だけapplyすることに基づく。次回SDK更新時に再確認が必要。
- UC8179画像gray timing、UC8279 variant別AA LUTを含む。host bus検証は通過したが、見た目・電気特性は未検証。

## 採用判断と次の順序

1. **指定SDKを維持し、#104の復旧効果は採用評価から除外**。製品sleep APIとバイナリは変更しない。
2. X3/X4の確認済み範囲では今回更新による不具合の報告なし。Stage 1は、X3-7の傾き方向/OFF確認保留、X4-5の電気的測定未実施、SDK #104の復旧効果除外、X4C実機未検証を明記して採用する。全項目合格とは扱わない。abortログが出ないことは異常の不存在を証明しない。
3. 次のv0.8.0項目は **X4C/X4V2基盤整理を先行**。未知VERの方針、NVS個体差、実機ログ、profile/driver/RTC/SDMMCの確認を優先する。
4. その後 **CrossPoint #3652 main-loop競合改善**。v0.7.8の先読み・章生成との相性を独立差分で検証する。

X4C実機が得られない場合もExperimentalを維持し、確認待ちを解消したことにせず、#3652の独立調査へ進める。
