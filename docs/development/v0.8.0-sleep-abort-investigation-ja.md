# Stage 1 sleep-abort追加調査

2026-09-28。対象SDK: `18e73e16a1965fb19c62fa3a717cbc3a5b43add3`。

## 結論

原因はSDK #104が「呼び出し元に戻らないAPI」の後ろに復旧処理を置いていること。
`noreturn`によるコード除去は確認済みだが、さらにIDF内部にも `abort()` があり、
宣言だけ回避してもSDKの復旧処理へは戻らない。

**SDK更新で正常sleepが壊れた証拠はない。この問題の修正を実機確認の前提にした以前の判断を訂正する。**
現revision・既存sleep APIを維持し、#104の効果を評価から外してX3/X4の実機確認へ進むのが推奨。
調査時点では実機確認待ちだった。その後の確認結果と保留事項付きの採用判断は [Stage 1検証報告](v0.8.0-freeink-stage1-ja.md) を参照。今回の調査自体では製品コード・SDK・binは変更していない。

## 調査根拠

### 1. 実際のAPI宣言と実装

使用中のArduino同梱ヘッダーはIDF 5.5.2を示し、`esp_sleep.h:622` で
`esp_deep_sleep_start()` に `__noreturn__` が付く。
ローカルframework-espidfのversionは `5.5.2.260206`。
Arduino libsのpackage表示は `5.5.0+sha.87912cd291` であるため、パッケージ名だけで版を決めず、
実ヘッダー・実バイナリ・公式ソースの該当関数を照合した。

公式v5.5.2実装では、通常APIはsleep rejectionを禁止して内部処理を呼び、
それでも戻れば `abort()` を呼ぶ。対してtry APIはrejectionを許可してエラーを返す。
[ESP-IDF v5.5.2実装](https://github.com/espressif/esp-idf/blob/v5.5.2/components/esp_hw_support/sleep_modes.c#L1223-L1235)

これは通常のsleep/wake後に同じ関数へreturnするという意味ではない。
deep sleep成功後のwakeは新しいbootになる。

### 2. リンク済みC3/S3の逆アセンブル

Stage 1で成功した `default` と `x4c` のELFを、それぞれのEspressif toolchainで確認した。

| 対象 | 実生成コード |
|---|---|
| C3 `esp_deep_sleep_start` | `a0=0` → `deep_sleep_start.isra.0` → `abort` |
| S3 `esp_deep_sleep_start` | `a10=0` → `deep_sleep_start$isra$0` → `abort` |
| C3/S3 SDK `PowerManager::deepSleep` | IDF呼び出し後のRTC記録・`esp_restart`なし |

出力ログ: `logs/idf-sleep-entry-c3.txt`, `logs/idf-sleep-entry-s3.txt`。
前回のSDK側証拠: `logs/abort-disassembly-c3.txt`, `logs/abort-disassembly-s3.txt`。
これらは調査報告と同じoutputsフォルダー内に保存した。

旧SDK `bc31e96` も同じ通常APIを呼び、直後にbusy loopを置いている。
そのloopも同じAPI契約では到達しない。旧SDKのloopが実際に電池消耗を起こしたとする証拠は得ていない。

### 3. 上流PRの確認

PR #104の説明とコメントを読み、作者自身もこのabort経路を再現していないことを確認した。
作者が調査していたX3の電池問題はSD電源レールの別件だったとの説明がある。
[PR #104](https://github.com/Free-Ink/freeink-sdk/pull/104)、
[作者の再現状況説明](https://github.com/Free-Ink/freeink-sdk/pull/104#issuecomment-5708172762)

上流の主張をYomukaの実機確認済み事実として扱わない。Yomuka Issue #40の原因とも結び付けない。

## 対処案の比較

| 案 | 評価 |
|---|---|
| 指定SDK・通常APIを維持 | 推奨。既存sleepの意味を保ち、#104の機能評価だけを除外して実機回帰へ進める |
| `esp_deep_sleep_try_to_start()`へ変更 | 戻り値で拒否を扱えるが、rejection許可という動作変更。Stage 1の単純互換修正にはしない |
| `noreturn`を外す、関数ポインター・別wrapperで隠す | IDF内部のabortを回避できず、目的を達成しない |
| リンカーwrapで通常APIをtry APIへ差し替える | SDK revision表示が同じでも実際の動作が変わる。今回は採用しない |
| SDK mainへ更新 | 今回の段階更新範囲外。問題の回避目的で一気更新しない |

try APIは有効なwake条件がsleep要求前に成立した場合などに拒否を返し得る。
通常APIとは契約が違うことを公式ドキュメントでも確認した。
[ESP-IDF sleep API](https://docs.espressif.com/projects/esp-idf/en/v5.5.2/esp32c3/api-reference/system/sleep_modes.html#_CPPv427esp_deep_sleep_try_to_startv)

将来try APIを採用する場合は、少なくともエラーコードを記録し、ボタン・レールhold・再起動の反復を検証する。
SDKの `wakeupCause` はtry APIの返却エラーコードではないため、それだけで拒否理由を特定できない。
通常sleep・拒否・再起動後の一回取得について、host注入とC3/S3実機を分けて検証する必要がある。
本調査ではこの設計変更・試作・実機注入は行っていない。

## 既存の異常診断と今回の限界

同梱C3/S3設定は `CONFIG_ESP_SYSTEM_PANIC_PRINT_REBOOT=1`。
Yomukaは `HalSystem::isRebootFromPanic()` でpanicを判別し、SD初期化後の `checkPanic()` で
`/crash_report.txt` を保存する経路と、crash report画面を持つ。
S3のstack復元はC3と同じ実装ではないため、同等のstack詳細が得られるとは断定しない。

従って内部異常は既存panic経路で診断する設計であり、SDKのabortフラグとは別物。
本調査はコード・設定・生成物の確認であり、実機で内部abortを起こして再起動・SD保存を確認したものではない。
電源保持・SDの状態によって記録が残る保証もしていない。

Stage 1で追加した `takeAbortedSleepInfo()` の呼び出しとRAM保持はそのまま残す。
このSDK/IDFの通常経路では有効な記録を生成できないため、
`previous_deep_sleep_aborted=false` は「SDK記録がない」という意味に限定する。
「前回sleepは確実に正常」「電源異常なし」の証明には使わない。
hostテストで確認済みなのは、記録をstubで与えた場合の取得・保持・通常無出力だけ。
